# F06: Persistence foundation: single-writer SQLite, migration ladder, journal, and integrity checks

**Planned labels:** `type:feature` `area:orchestration` `risk:high` `phase:0` `ready-for-agent`  
**Depth in the DAG:** 2 · **Direct blockers (published, transitively reduced):** F02

> Symbolic key: `F06` · Area: orchestration · Phase: 0 · Risk: high

## 2. Objective
State and an append-only journal persist atomically in SQLite, with ordered migrations, pre-migration backup, integrity checks, and post-commit event publication.

## 3. Requirement IDs
FR-019, FR-023, FR-046, NFR Reliability

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- Writer thread with command channel; read-only connections; WAL; foreign keys; embedded SQL migration ladder keyed by user_version with backup and restore-on-failure.
- Initial schema for projects, build_runs, event_journal, operations, settings; journal append with monotonically increasing seq and last_event_seq on rows.
- Post-commit publication to subscribers; startup integrity check.
- Migration files and `repositories/` modules are discovered by a `build.rs` directory scan, so adding a table adds files and edits no shared list; each migration-owning ticket also owns its own `repositories/<ticket>_*.rs` files (SHARED_SURFACE_PROTOCOL.md section 3).
- The ladder discovers `NNNN_<ticket>_<name>.sql` files and applies them in numeric order from an empty database, tolerating gaps, so tickets use the reserved blocks in SHARED_SURFACE_PROTOCOL.md section 3 and cannot collide.
- Also creates the `state_store_backups` table recording each backup (path, schema version, created time); a backup is taken before any migration.
- Fault-point tests use the F02 fault mechanism with the re-exec pattern; F06 does not wait for the F03 harness.

## 6. Architectural constraints
- The Orchestrator is the only writer of orchestration state; each transition is one transaction (state plus journal) (ADR-002, ADR-017).
- Events reach the UI only after commit.
- Scheduler never assumes a UI is open.

## 11. Acceptance criteria
- [ ] A transition writes state and journal in one transaction; a kill between them leaves neither or both (fault-point test).
- [ ] Migrations apply forward; a failing migration restores the backup and refuses to run newer logic.
- [ ] State/journal mismatch is detected as an integrity failure and never silently repaired.
- [ ] Events publish only after commit.
- [ ] Two migration files with reserved, non-adjacent numbers apply in numeric order regardless of the order in which they were merged (test), and a duplicate number fails the test suite.

## 12. Required unit tests
- Transaction atomicity; seq monotonicity; migration ordering; backup/restore.

## 13. Required integration tests
