# K05: vela-uia discovery and read: windows, warm-up, correlation, and card observation

**Planned labels:** `type:feature` `area:broker` `risk:high` `phase:2` `ready-for-agent`  
**Depth in the DAG:** 2 · **Direct blockers (published, transitively reduced):** SP02, K04, F02

> Symbolic key: `K05` · Area: broker · Phase: 2 · Risk: high

## 2. Objective
Vela finds Vela-correlated Antigravity windows, warms up the accessibility tree, and observes the approval card without interacting.

## 3. Requirement IDs
FR-033, FR-039, AT-014

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- UIA wrapper per the bindings spike; window discovery by process; warm-up and retry; correlation (title, assembled command text, working directory, status text); fail-closed ambiguity; Windows-only crate.

## 6. Architectural constraints
- Policy and delivery are separate; no adapter decides safety (ADR-007).
- Vela approves operations, not buttons; fail closed on any ambiguity.
- UI automation is opt-in and consent-gated (ADR-010).

## 7. Dependencies / blocked by
- SP02 Spike S-UIA-BINDINGS: does the windows crate expose the UI Automation interfaces Vela needs?
- K04 Fake approval window harness reproducing the verified card roles
- F02 Domain primitives, ports, and TypeScript contract generation

## 8. Expected write surfaces
- crates/vela-uia/src/discovery/**

## 9. Known shared contracts
- ApprovalSource and ApprovalDeliveryAdapter ports
- approval tables (requests, decisions, delivery attempts, fingerprints, policy rules)

## 10. Parallelization notes
Parallel with K02.

## 11. Acceptance criteria
- [ ] Against the fake window the adapter finds the card and assembles the command fragments.
- [ ] It fails closed on duplicate cards, a minimized window, and a non-correlated window.
- [ ] Unrelated Approve buttons are never matched.
