# D06: Review domain: finding identity, exit policy, review stages, and verification verdicts

**Planned labels:** `type:feature` `area:domain` `risk:medium` `phase:1` `ready-for-agent`  
**Depth in the DAG:** 2 · **Direct blockers (published, transitively reduced):** F02

> Symbolic key: `D06` · Area: domain · Phase: 1 · Risk: medium

## 2. Objective
Review findings have stable ids, Vela decides blocking from the Engineering exit policy, and the review domain permits exactly one comprehensive review per ticket followed by targeted verification, with every failure ending in human escalation and never in approval (ADR-022).

## 3. Requirement IDs
FR-013, FR-014

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- Finding fingerprint (category, location, requirement); disposition tracking; exit policy evaluation.
- Review cycle model: `stage` (`COMPREHENSIVE` or `VERIFICATION`), at most one `COMPREHENSIVE` cycle per ticket unless a user decision requests another, a `VERIFICATION` cycle only after a fix set, and per-finding verification verdicts (`RESOLVED` or `NOT_RESOLVED`; a missing verdict is `NOT_RESOLVED`).
- Verification outcome evaluation: pass only when the comprehensive review had no blocking finding, or every blocking finding is `RESOLVED`, the fix diff has no blocking finding and no high-severity finding is open; every other outcome yields escalation (`NEEDS_HUMAN`, kind `REVIEW_STALLED`). No iteration cap and no oscillation detection exist: a review is not repeated.

## 6. Architectural constraints
- vela-domain depends on no other Vela crate and has no I/O (pure logic).
- Provider-specific concepts do not leak into domain types (ADR-006).

## 11. Acceptance criteria
- [ ] The same finding keeps its id from the comprehensive review into the verification.
- [ ] Exit policy matches REVIEW_PROTOCOL.md.
- [ ] A second comprehensive review is rejected unless it carries a user decision, whatever the other inputs (fixed-point advance, retry, recovery).
- [ ] Every failed verification (unresolved blocking finding, blocking defect in the fix diff, open high-severity defect, missing verdict) yields escalation to `NEEDS_HUMAN` with kind `REVIEW_STALLED`; no input sequence yields success while a blocking finding is unresolved, and no human decision or timeout approves one (property test).

## 12. Required unit tests
- Policy tests; stage and cycle-count rules; verification outcome table over every combination of verdicts, fix-diff findings and high-severity observations; property test that success is unreachable with an unresolved blocking finding.
