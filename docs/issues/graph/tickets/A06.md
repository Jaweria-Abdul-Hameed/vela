# A06: Native policy enforcement and the posture probe (MEETS, DOES_NOT_MEET, UNKNOWN)

**Planned labels:** `type:feature` `area:antigravity` `risk:high` `phase:2` `ready-for-agent`  
**Depth in the DAG:** 6 · **Direct blockers (published, transitively reduced):** A05, A04, SP04, SP06, A03

> Symbolic key: `A06` · Area: antigravity · Phase: 2 · Risk: high

## 2. Objective
Vela enforces ALLOW, DENY, and ASK natively through allow rules plus the deny hook and reports the effective posture; Autonomous mode is available only when it is MEETS.

## 3. Requirement IDs
FR-036, FR-038, AT-015

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- Hook registration at the verified location; posture probe scenarios (deny blocks, unlisted denied, allow runs, hook failure blocks); posture result persisted and shown in preflight; integrity checks of policy files.

## 6. Architectural constraints
- Only vela-adapters::antigravity and vela-uia may contain Antigravity-specific behavior (ADR-008, ADR-018).
- Never trust exit code or result.status; interpret events, stderr, and Git state.
- Never read, copy, or persist Antigravity credentials or tokens (ADR-016).
- Elements tagged [U] are gated by their spike; do not claim them ready.

## 7. Dependencies / blocked by
- A05 Per-worker profile manager and generated settings and allow rules
- A04 vela-hook binary, rule-table format, and spool records (fail-closed)
- SP04 Spike S-NATIVE-POSTURE: do generated allow rules plus a fail-closed hook enforce ALLOW, DENY, and unknown?
- SP06 Spike S-HOOK-GLOBAL: are global-path hooks in an isolated profile loaded, and are policy files protected from agent writes?
- A03 Per-turn session driver: spawn, conversation id, explicit timeout, cancel, resume
