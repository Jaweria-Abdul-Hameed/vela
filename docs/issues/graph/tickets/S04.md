# S04: Preflight engine end to end: repository, toolchain, trust, and Windows checks with severity table

**Planned labels:** `type:feature` `area:orchestration` `risk:medium` `phase:1` `ready-for-agent`  
**Depth in the DAG:** 7 · **Direct blockers (published, transitively reduced):** S03, O01

> Symbolic key: `S04` · Area: orchestration · Phase: 1 · Risk: medium

## 2. Objective
Running preflight on a project yields a PASS/WARN/BLOCK report per the severity table, shown in a preflight panel.

## 3. Requirement IDs
FR-002, AT-001

## 4. User-visible behavior
A preflight panel with checks, remediation actions, and blocking reasons in plain language.

## 5. Technical scope
- Repository, trust, toolchain (manifests read as data, no scripts run), Git/GitHub, docs, and Windows checks (synced folders, path length, submodules, Git version, line endings); severity table; remediation actions; recorded setup.

## 6. Architectural constraints
- The Orchestrator is the only writer of orchestration state; each transition is one transaction (state plus journal) (ADR-002, ADR-017).
- Events reach the UI only after commit.
- Scheduler never assumes a UI is open.

## 7. Dependencies / blocked by
- S03 Repository trust: untrusted by default, trust sheet, data-only analysis, Build refusal
- O01 Orchestrator actor skeleton: message bus, transactional transitions, run creation, snapshot assembly

## 8. Expected write surfaces
- crates/vela-core/src/preflight/**
- apps/desktop/src/surfaces/preflight/**

## 9. Known shared contracts
- EventEnvelope and the closed journal vocabulary (SYSTEM_ARCHITECTURE.md section 4)
- State-machine tables in vela-domain
- Preflight report DTO

## 10. Parallelization notes
Antigravity and approval checks are added later (A01, K10).
