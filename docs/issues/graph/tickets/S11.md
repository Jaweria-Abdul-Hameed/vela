# S11: Checkpoint and review workflow with a fake reviewer: fixed point, one review, fixes, verification

**Planned labels:** `type:feature` `area:orchestration` `risk:high` `phase:1` `ready-for-agent`  
**Depth in the DAG:** 11 · **Direct blockers (published, transitively reduced):** S10, G03, D06

> Symbolic key: `S11` · Area: orchestration · Phase: 1 · Risk: high

## 2. Objective
After validation Vela checkpoints, runs exactly one authoritative comprehensive review at the fixed point, fixes blocking findings with regression tests, retests, and runs a targeted independent verification; if any blocking finding remains it escalates to a human and never repeats a full review automatically (ADR-022).

## 3. Requirement IDs
FR-013, FR-014, FR-015, AT-004

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- Checkpoint invariant; fixed point and its advancement; finding identity from review into verification; the review stages (one `COMPREHENSIVE` cycle, then a `VERIFICATION` cycle after each fix set: review fixes, fixes after a failed integration validation, a conflict resolution); the pre-review gate (checkpoint with required gates green); escalation of a failed verification to `NEEDS_HUMAN` kind `REVIEW_STALLED`; user decisions that direct a fix, request a new comprehensive review, or cancel; seeded-defect scenario. The worker state machine (D01) is not changed: the first `REVIEWING` visit is the comprehensive review and each later visit a verification.
- Recovery: a review or verification interrupted before its result is recorded is re-run as the same cycle by operation id; a recorded result is never replayed; recovery never starts a comprehensive review for a ticket that has a recorded one.
- Persists the stage, the per-finding verdicts and one reviewer conversation id per cycle (the comprehensive reviewer's and the verifier's).
- Owns the `evidence.get` read command (commands, test runs, review findings), reserved migration block 0100-0109 (`review_cycles`, `review_findings`, `git_checkpoints`, reviewer conversation-id column), and the FaultPoints at checkpoint and review transitions.

## 6. Architectural constraints
- The Orchestrator is the only writer of orchestration state; each transition is one transaction (state plus journal) (ADR-002, ADR-017).
- Events reach the UI only after commit.
- Scheduler never assumes a UI is open.

## 11. Acceptance criteria
- [ ] The seeded defect produces one comprehensive review, finding, fix with a regression test, tests, checkpoint, targeted verification in a distinct fresh conversation, pass (AT-004).
- [ ] A verification that leaves a blocking finding unresolved, finds a blocking defect in the fix diff, or finds an open high-severity defect yields NEEDS_HUMAN with kind REVIEW_STALLED, with no second full review, no automatic repair round and never success.
- [ ] No sequence of fixed-point advancement, retry, crash and recovery, or Stop All and resume starts a second comprehensive review; a recorded user decision does.
- [ ] A crash before a review result is recorded re-runs the same cycle; a crash after it never repeats the review (kill-and-restart harness).
- [ ] The reviewer and verifier conversation ids are recorded per review cycle.

## 12. Required unit tests
- Fixed-point advancement to the merged integration tip (never starts a review); review stage sequencing; finding id stability from review into verification (via D06); each failed-verification case produces NEEDS_HUMAN with kind REVIEW_STALLED; user decisions (direct a fix, new comprehensive review, cancel) and the absence of any decision that approves a blocking finding.

## 13. Required integration tests
