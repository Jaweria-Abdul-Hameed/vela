# S15: Human intervention model: records, kinds, resume state, decisions

**Planned labels:** `type:feature` `area:orchestration` `risk:high` `phase:1` `ready-for-agent`  
**Depth in the DAG:** 6 · **Direct blockers (published, transitively reduced):** O01

> Symbolic key: `S15` · Area: orchestration · Phase: 1 · Risk: high

## 2. Objective
Anything needing a human becomes an intervention record with preserved work, last safe commit, evidence, actions, and consequences, resolvable back to the recorded resume state (independent of the worker lifecycle implementation).

## 3. Requirement IDs
FR-020, AT-010

## 4. User-visible behavior
Data for the intervention sheet (rendering in the UI ticket).

## 5. Technical scope
- Intervention persistence and journal; kinds from ORCHESTRATION_ENGINE.md; resolve command returning the run or worker to resume_state.
- A per-kind resolution precondition, registered by the owning module through the Orchestrator service registry (default: none). `PROVIDER_POLICY_BLOCK` has no automatic resolution; its precondition is registered by S16.

## 6. Architectural constraints
- The Orchestrator is the only writer of orchestration state; each transition is one transaction (state plus journal) (ADR-002, ADR-017).
- Events reach the UI only after commit.
- Scheduler never assumes a UI is open.

## 11. Acceptance criteria
- [ ] Intervention records for run-level kinds (GRAPH_INVALID, INTEGRATION_UNKNOWN) and worker-level kinds are created, persisted, journaled, and resolved through intervention.resolve against the state machines using fakes.
- [ ] Resolving returns to the recorded resume_state.
- [ ] A kind with a registered precondition cannot be resolved until the precondition holds; a fake precondition for `PROVIDER_POLICY_BLOCK` proves the resolve is rejected while it fails and accepted once it holds.
- [ ] The AT-010 end-to-end ambiguity scenario is verified with the worker lifecycle in Z03 and in S10 once both exist; this ticket supplies the model and commands.
