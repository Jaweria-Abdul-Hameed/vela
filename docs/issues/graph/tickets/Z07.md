## 2. Objective
The installer, first launch, upgrade, and uninstall behavior of Vela is validated on the clean Windows 11 virtual machine that H05 provisions, and every result, limitation, and NOT VERIFIED item is recorded as evidence. This is the one ticket that needs the clean environment for installer and lifecycle evidence; it owns the validation runs, not the installer (Z01), the updater (Z02), or the final production release gate (Z06).

## 5. Technical scope
- Environment model from H05: **S0** pristine baseline, **S1** N-1 installed (derived from S0), **S2** runtime-prerequisite state with Git (derived from S0, created only if a scenario needs it). The guest is the Windows 11 Enterprise 90-day Evaluation, not Windows Home, and is time-limited; a different edition is tested only if release validation deliberately requires it. Record per run: Windows build and edition, snapshot, WebView2 runtime version, Smart App Control and SmartScreen state, network state, guest tools, and the date.
- Scenarios on S0, reverting after each: pristine install of the development-signed installer from Z01; first launch with no Git and no Antigravity, showing the documented missing-prerequisite behavior (preflight reports the missing prerequisites and remediation without a crash); an installed-software listing proving no Rust, Node, or Visual Studio build tooling is needed or present; development Authenticode verification with built-in Windows facilities (`Get-AuthenticodeSignature`) on the installer and the bundled `vela-hook`; login auto-start (the entry L03 creates from the onboarding choice of L01 is present, and the app launches at login after a guest reboot); and uninstall (installed files and shortcuts removed, the auto-start entry removed, repositories untouched, Vela data kept by default). Evidence that needs the complete product running a real workload belongs to Z06, not here: tray and background operation, hide-on-close, reboot continuation of a real run, notifications with the window closed (clean-machine evidence for AT-019 and AT-023), and termination of the running app and its tray icon at uninstall. Z07 does not wait for L02, R07, or S17 because none of its own evidence exercises them.
- Scenario on S1: the real-machine upgrade from the N-1 installer artifact to N produced by Z02 (state store preserved, migrations applied after a backup, rollback on a failed migration, the WebView2 refresh prompt), executing Z02's updater; implementation and simulation tests remain Z02's, and this ticket supplies the clean-machine evidence for AT-024.
- WebView2: record the runtime version present. Verify the configured bootstrapper, embedded, and offline distribution behavior where technically possible (the offline installer with the network off; the bootstrapper path where it can be exercised). Windows 11 includes the Evergreen runtime and no supported removal is established, so a genuinely WebView2-absent state is not a prerequisite and unsupported removal is forbidden: if no supported method yields an absent state, record the missing-runtime path as **NOT VERIFIED** with the reason, never as passed.
- Smart App Control and SmartScreen: not mandated on or off; record the actual state with each run. A rejection of a development or self-signed artifact under an enforcing posture is expected evidence, not an application failure. Production-signed behavior is Z06's, which reuses this environment.
- Artifact transfer: the artifact and its SHA-256 manifest are created outside the guest and move in by a read-only virtual disk or ISO; hashes are verified in the guest with built-in facilities; no permanent shared folder, drag-and-drop, or clipboard dependency on the pristine baseline; the network is off unless a scenario needs it; revert to the appropriate snapshot after each scenario.
- The verification scripts run in the guest (hash check, software listing, signature report) live under `tests/e2e/clean-machine/**` and use only built-in Windows facilities, so the baseline needs no extra tooling.

## 6. Architectural constraints
- No FAIL item may be silently waived and no unverified item silently passed; evidence, including NOT VERIFIED with its reason, is recorded per checklist item.
- No host setting is changed (no Windows feature, BIOS or UEFI, VBS, Memory Integrity, Smart App Control, or WSL change). No credentials, license keys, signing keys, or Antigravity authentication enter the guest or the repository.
- The evaluation guest is never extended by unsupported means; when it lapses it is re-provisioned by H05.
- Quiet-machine workload on a 16 GB host: do not run concurrently with PF1, heavy Antigravity worker activity, or large WSL workloads.

## 11. Acceptance criteria
- [ ] S0 install, first launch, no-development-tooling listing, development Authenticode verification, and uninstall each have recorded evidence (hash manifest verified in the guest, installed-software listing, signature report, post-uninstall listing showing installed files, shortcuts, and the auto-start entry removed and repositories untouched).
- [ ] First launch without Git and Antigravity shows the documented missing-prerequisite behavior with no crash, and the behavior is recorded.
- [ ] Login auto-start is evidenced on the clean guest (the entry exists after onboarding, the app launches at login after a guest reboot, and the entry is gone after uninstall), or the unsupported part is recorded as NOT VERIFIED with its reason. Tray, background, reboot continuation of a real run, and notification evidence are Z06's.
- [ ] The N-1 to N upgrade on S1 preserves the state store, applies migrations after a backup, and rolls back on a failed migration, with evidence from two real installer artifacts.
- [ ] The WebView2 runtime version and the configured distribution modes are recorded, with every mode that could not be exercised (including the missing-runtime path, if no supported absent state exists) marked NOT VERIFIED with a reason.
- [ ] Every run records the Windows build and edition (Enterprise Evaluation, not Home), the Smart App Control and SmartScreen state, the snapshot, and the network state; no state is mandated on or off.

## 18. Non-goals

- Implementing any other ticket in the graph; only small prerequisite fixes strictly needed for correctness, recorded in the execution log.
- Adding Claude, Codex, or any other production runtime adapter (ADR-008).
- Reopening or redesigning accepted ADRs; contradictions become a NEEDS_HUMAN decision request.
