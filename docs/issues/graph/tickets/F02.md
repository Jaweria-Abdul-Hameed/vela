# F02: Domain primitives, ports, and TypeScript contract generation

**Planned labels:** `type:feature` `area:domain` `risk:medium` `phase:0` `ready-for-agent`  
**Depth in the DAG:** 1 · **Direct blockers (published, transitively reduced):** F01

> Symbolic key: `F02` · Area: domain · Phase: 0 · Risk: medium

## 2. Objective
vela-domain defines the identifiers, value objects, error classes, and every port trait, and the TypeScript contract package is generated from them with a contract test scaffold.

## 3. Requirement IDs
NFR Provider independence, NFR Testability, FR-029

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- Value objects (RunId, TicketId, WorkerId, CommitSha, BranchName, WorktreePath, GateResult, ReviewSeverity, DependencyEdge, RiskClass).
- All ports in IMPLEMENTATION_ARCHITECTURE.md section 3 as traits with typed errors (ERROR_HANDLING.md classes).
- EventEnvelope and the closed event-kind vocabulary; ts-rs derivations exporting to packages/contracts/src/generated.
- The provider-neutral `PROVIDER_POLICY_BLOCK` typed error (class POLICY_BLOCK, origin provider), the neutral `ProviderPolicyBlock` agent event, and the journal kinds `ProviderPolicyBlockRecorded` and `ProviderPolicyBlockCleared` in the closed vocabulary (SYSTEM_ARCHITECTURE.md section 4), with no provider-specific wording (ADR-006).
- Command-registry type and a contract test that fails when a Rust command lacks a TypeScript wrapper or vice versa (scaffold; real commands arrive later).
- `vela-domain::fault`: the `FaultPoint` enum (points are registered by the owning tickets), a `fault_point!` macro that compiles to nothing unless the `fault-injection` feature is enabled, and an environment-variable armed abort hook. The kill-and-restart harness is F03 (SHARED_SURFACE_PROTOCOL.md section 6).
- Define `GitAdapter` and `AgentAdapter` as composed capability traits (for example GitRead, GitWorktrees, GitCheckpoints, GitMerges, GitRemote; AgentSession, AgentProfile, AgentReviewer) with the existing port names as supertraits, so the tickets that implement each capability edit separate impl blocks and files.
- Typed (ts-rs) payload DTOs for every event kind in the closed vocabulary, so the reducer and UI fixture streams are typed against real payload shapes.
- Expose generated types through a `packages/contracts` `exports` wildcard (`./generated/*`) with no hand-edited barrel (SHARED_SURFACE_PROTOCOL.md section 4).
- Declare the Cargo features `fault-injection` and `hook-table` in `vela-domain/Cargo.toml` so D05 and A04 add modules under the feature without editing the manifest.

## 6. Architectural constraints
- vela-domain depends on no other Vela crate and has no I/O (pure logic).
- Provider-specific concepts do not leak into domain types (ADR-006).

## 10. Parallelization notes
Blocks nearly everything. Do not run other domain tickets concurrently with the port definitions; after it merges, domain tickets are independent because each owns its own module and F01 declared the module skeleton.

## 11. Acceptance criteria
- [ ] All ports and value objects compile with documentation; ts-rs export runs under cargo test and produces TypeScript that typechecks.
- [ ] The event vocabulary matches SYSTEM_ARCHITECTURE.md section 4 exactly (a test enumerates it).
- [ ] The contract test scaffold passes with an empty registry and fails with a seeded mismatch.
- [ ] With the `fault-injection` feature off, `fault_point!` generates no code (compile test); with it on, an armed point aborts the process.
- [ ] Every event kind in the vocabulary has a typed payload DTO with a serialization round-trip test.
- [ ] The capability traits compose into the original port names, and a test double implementing only one capability compiles.
