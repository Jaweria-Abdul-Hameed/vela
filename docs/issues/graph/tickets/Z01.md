# Z01: Installer: NSIS per-user package with development signing, WebView2 handling, and uninstall behavior

**Planned labels:** `type:feature` `area:release` `risk:high` `phase:7` `ready-for-agent`  
**Depth in the DAG:** 4 · **Direct blockers (published, transitively reduced):** F04, A04

> Symbolic key: `Z01` · Area: release · Phase: 7 · Risk: high

## 2. Objective
A development-signed NSIS per-user installer is built that installs without development tooling and uninstalls cleanly by construction. Running it on the clean Windows environment and recording the evidence belongs to Z07 (which needs H05); this ticket needs no VM.

## 3. Requirement IDs
FR-047

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- Tauri bundler NSIS per-user; WebView2 bootstrapper mode (embedded and offline options); Windows Authenticode signing pipeline; uninstall behavior; no localhost dev server.
- Bundle `vela-hook` as a signed sidecar or resource with a stable installed path that the profile generator resolves through the W01 path function.
- Uninstall removes the tray entry, auto-start entry, and shortcuts; it never touches repositories and keeps Vela data unless the user chooses removal (default keep).
- This ticket owns the Authenticode signing mechanism and its development-signed proof, and needs no production material. Authenticode is not the Tauri updater signature (Z02).
- Build profiles: a **development profile** signs with a throwaway self-signed development certificate (generated locally or in CI, never committed, never represented as production trust material, selected through the `tauri.dev-signing.conf.json` overlay). A **production profile** takes the Authenticode route and credentials from release secrets and variables that H04 supplies, and fails closed if they are absent or if a development certificate is detected. Executing the production profile and verifying its result belong to Z06.
- Documents the development-signing procedure in `docs/release/DEV_SIGNING.md`, including that Smart App Control (observed ON on the current development machine) may block unsigned or self-signed development artifacts. Changing that setting is not part of this ticket and not a development prerequisite: surface an actual blocker instead of weakening it. Installer run evidence on the clean environment (provisioned by H05) is Z07's.
- Implementation-level proof without a VM: the build asserts the produced bundle (per-user install mode, the `vela-hook` sidecar at its stable path, the configured WebView2 mode, uninstall entries) and verifies the Authenticode signature on the build host with built-in Windows facilities.

## 11. Acceptance criteria
- [ ] The build produces a per-user NSIS installer whose bundle contains no development-tool dependency and whose uninstall entries remove the tray entry, auto-start entry, and shortcuts and leave repositories untouched (asserted on the produced bundle; the install and uninstall runs on a clean machine are Z07's).
- [ ] The WebView2 runtime is handled in the configured bootstrapper mode, with the embedded and offline options available as build options (the produced installer reflects the configured mode).
- [ ] Authenticode (not the updater signature): the installer and the bundled `vela-hook` carry an Authenticode signature from the development certificate that built-in Windows verification (`Get-AuthenticodeSignature`) reports as signed by that certificate on the build host, and the artifact is labelled as development-signed.
- [ ] A production-profile build with no production credentials fails closed, and a production-profile build that would sign with a development certificate fails closed.
