# Z02: Updater: signed updates, deferral during runs, pre-update backup, rollback

**Planned labels:** `type:feature` `area:release` `risk:high` `phase:7` `ready-for-agent`  
**Depth in the DAG:** 13 · **Direct blockers (published, transitively reduced):** Z01, R05, R04

> Symbolic key: `Z02` · Area: release · Phase: 7 · Risk: high

## 2. Objective
Updates are signed with the Tauri updater signature (verified here with a disposable test keypair), never applied during an active run, and back up state first with rollback on failure. No production signing material is needed.

## 3. Requirement IDs
FR-047, AT-024

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- Updater plugin with signature verification; can_apply refusal during runs; explicit user action after quiescence; pre-update backup; failed-migration rollback; WebView2 runtime refresh prompt.
- The updater signature is Tauri updater artifact signing, which is not Windows Authenticode (Z01). Development and tests use a **disposable test updater keypair**: the private key is generated into a test temporary directory (never committed, never reused for production), and its public key is supplied through the `tauri.updater-test.conf.json` overlay. The committed base configuration contains no production updater key. A release-profile build takes the production public key only from the value H04 records, and fails closed if the test key is configured.
- The update endpoint is configuration; tests use a local test update server. The final production hosting location is an H04 decision, not made here. Documents the test-key procedure and the key-separation rules in `docs/release/UPDATER.md`.

## 11. Acceptance criteria
- [ ] An update available during a run is deferred; applying after quiescence backs up state; a failed migration restores it (AT-024).
- [ ] Updater integration tests show that an upgrade from build N-1 to build N preserves the state store, applies migrations after a backup, and rolls back on failure. The same ticket produces the two installer artifacts (N-1 and N, built and signed with development and test material) and the procedure that Z07 runs on the clean environment; the real-machine N-1 to N run and its evidence are Z07's, and this ticket needs no VM.
- [ ] Updater signature (not Authenticode): an update artifact signed with the test updater key verifies and installs in simulation; a tampered artifact and an artifact signed with a different key are rejected; a release-profile configuration that carries the test key fails closed.
