# D07: Approval domain: requests, decisions, fingerprints, progress definition, loop-guard counters

**Planned labels:** `type:feature` `area:broker` `risk:medium` `phase:2` `ready-for-agent`  
**Depth in the DAG:** 3 · **Direct blockers (published, transitively reduced):** D05, D01

> Symbolic key: `D07` · Area: broker · Phase: 2 · Risk: medium

## 2. Objective
Approval requests are fingerprinted without secrets and the loop guard counts repeats with a precise progress definition.

## 3. Requirement IDs
FR-034, FR-035

## 4. User-visible behavior
None (no user-visible behavior).

## 5. Technical scope
- ApprovalRequest, ApprovalDecision, fingerprint (provider, worker, operation class, command family, working root, target category); progress signals; threshold default 3.

## 6. Architectural constraints
- Policy and delivery are separate; no adapter decides safety (ADR-007).
- Vela approves operations, not buttons; fail closed on any ambiguity.
- UI automation is opt-in and consent-gated (ADR-010).

## 7. Dependencies / blocked by
- D05 Policy engine core: operation model, PowerShell and cmd normalizer, ordered rules, ALLOW/ASK/DENY
- D01 State machines: run, worker, and ticket projection with exhaustive transition tests

## 8. Expected write surfaces
- crates/vela-domain/src/approval/**

## 9. Known shared contracts
- ApprovalSource and ApprovalDeliveryAdapter ports
- approval tables (requests, decisions, delivery attempts, fingerprints, policy rules)

## 10. Parallelization notes
Parallel with other domain work after D05.

## 11. Acceptance criteria
- [ ] Repeated identical fingerprints without progress trip the threshold.
- [ ] Each progress signal resets it.
- [ ] No secrets in fingerprints.
