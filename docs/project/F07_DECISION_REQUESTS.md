# F07 Decision Requests

Interpretations F07 had to make where the specification is silent, and design limits it could not remove inside its own write surfaces. None changes user-visible behavior. Each is isolated in one place so a decision changes one rule. DR-F07-1 was called out by the reviewer as needing an owner decision before O01 builds on it; it does not block F07's own acceptance criteria.

## Known limits (recorded, not blocking)

- **Redaction is a safety net.** It recognizes names, schemes, token shapes, URL user information, PEM private keys and registered values. A secret with no recognizable name or shape and that was never registered is not found (for example the argument of `curl -u user:pass`, or a password printed alone on a line). `CommandSpec` keeps secrets in the environment for that reason, and P01 should register the credential-like environment values of each process (`PatternRedactor::with_environment`).
- **Encodings.** A registered secret is matched as written. Its base64, URL-encoded or otherwise transformed forms are not matched. Token shapes are found inside percent-encoded and escaped text; names next to a percent escape are not.
- **Multi-line values.** Except for PEM private keys, a value that continues on the following lines (a YAML block scalar) is redacted only on its first line. An open private key swallows at most 256 lines when its `END` line never arrives.
- **Structure across lines.** The structural rules (credential containers, name and value pairs, the argument after a credential flag) apply to a JSON document that is given whole: a log record, a journal payload, a stream-json line. Pretty-printed JSON that arrives one line at a time, a document the walk rejects (nested deeper than 128, `NaN`) and a line cut at the limit are redacted line by line as text, where only names and shapes on the same line count.
- **`.netrc` on several lines.** `password value` on a line of its own, with a single blank, is not distinguishable from prose and is not redacted.
- **Numbers in a redacted payload.** A payload in which something was redacted is rebuilt from the redacted document; its untouched floating-point numbers are re-read from their decimal form. A payload with nothing to redact is not touched.
- **Typed payloads.** A redacted value is always a string, so a numeric field under a credential-like name would not deserialize after redaction. No event of the closed vocabulary has such a field; a ticket that adds one keeps credentials in string fields.
- **End-to-end test across the two crates.** The corpus runs through the real redactor at every ingestion point inside `vela-process` (plain text, chunked process output, the JSON log layer, serialized journal payloads). `vela-core::diagnostics::redact_payload` passes the serialized payload to the port unchanged, and is tested with a stand-in port because `vela-core` cannot use `vela-process` even as a dev-dependency. A test that joins the real redactor to the core port belongs to the composition root (W01) or the security regression suite (X04, `tests/integration/security/regression`).

## Follow-ups for other tickets (not code in F07)

- **F04 / W01:** install the subscriber (`json_layer` over `LogFile`), adapt the shared redactor to `RedactionPort` (`redact_text` to `Redactor::redact`, `redact_value` to `Redactor::redact_value`), route targets to streams, and add the cross-crate test named above.
- **P01:** wrap stdout and stderr in `StreamRedactor`; build the per-process redactor with `with_environment`; choose the line limit for stream-json; transcode UTF-16; call `flush_partial` when a stream goes quiet.
- **O01:** call `redact_payload` on every journal payload before it reaches the writer thread; open a `CorrelationIds` scope per run, worker and operation, and use `spawn_correlated` for worker tasks.
- **X03:** re-redact at export with the same port; retention by age.
