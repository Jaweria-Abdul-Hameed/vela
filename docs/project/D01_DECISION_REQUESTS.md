# D01 Decision Requests

Interpretations D01 had to make where `ORCHESTRATION_ENGINE.md` and `DOMAIN_MODEL.md` are silent or inconsistent. None changes product behavior beyond the conservative reading (reject what is not listed). Each is isolated in one place in `crates/vela-domain/src/state/` so a decision changes one rule. None is blocking.

| ID | Question | What D01 implemented | Where |
|---|---|---|---|
| DR-D01-1 | The diagram in section 1 draws `FINAL_FIXING` to `FINAL_VALIDATION` (`FINAL_REVIEW ⇄ FINAL_FIXING ⇄ FINAL_VALIDATION`) but the normative table 1.1 lists only `FINAL_FIXING` to `FINAL_REVIEW`. | The table wins: `FINAL_FIXING` to `FINAL_VALIDATION` is rejected. Likewise no direct `PAUSED`/`NEEDS_HUMAN` entry from `FINAL_*`, `CREATED`..`GRAPH_READY`..`AWAITING_START` except via `STOPPING` (Stop All), because the table lists direct entry only from `RUNNING`, `ANALYZING` (`GRAPH_INVALID`) and `STARTING`. | `run.rs` `PHASE_EDGES`, `Run::transition` |
| DR-D01-2 | Which `NEEDS_HUMAN` kinds are valid at run level? Section 3.2 says only `PROVIDER_POLICY_BLOCK` is "valid at worker and run level"; section 1.1 and 1.2 additionally name `GRAPH_INVALID`, `INTEGRATION_UNKNOWN`, `INTEGRATION_UNHEALTHY` as run-level kinds that are absent from the 3.2 table. | `InterventionKind` has 16 kinds: the 13 of 3.2 plus those 3. A worker accepts exactly the 13; a run accepts all 16 (no restriction invented). `GRAPH_INVALID` is required for `ANALYZING` to `NEEDS_HUMAN` and is rejected from every other origin. Section 3.2 should list the three run-level kinds. | `common.rs`, `run.rs` |
| DR-D01-3 | "No transition leaves `PROVIDER_POLICY_BLOCK` automatically; the only exits are resolve to `resume_state` or cancel" versus "any non-terminal to `FAILED`" and "any non-terminal to `STOPPING`". | Both are honored without any automatic exit: from a held block (worker and run) the accepted targets are `Active(resume_state)` by `Cause::UserDecision` (resolve), `CANCELLED`, `FAILED` (terminal; never resumes work), and, at run level, `StoppingProviderBlock` (Stop All that keeps the hold: it returns only to the same block, or fails, never to `PAUSED` or work). Every other target is rejected with `ProviderPolicyBlockHeld`. | `run.rs`, `worker.rs` |
| DR-D01-4 | The `PAUSED` reason and the `NEEDS_HUMAN` kind per edge. | Kinds are not constrained beyond the explicit rules above. `STOP_ALL` is reached only through `STOPPING` (`STOPPING` to `PAUSED` accepts only that reason; `RUNNING` to `PAUSED` rejects it; section 6). Section 3.1 ("any state can transition to ...") is read as: a `PAUSED` worker or run can escalate to `NEEDS_HUMAN` (so a provider policy block found while paused is recorded, never `RATE_LIMITED`); `NEEDS_HUMAN` back to `PAUSED` is not a transition. | `run.rs`, `worker.rs` |
| DR-D01-5 | Which worker states are "agent-driven" (so `WAITING_APPROVAL` can overlay them)? | `CONTEXT_LOADING`, `IMPLEMENTING`, `REVIEWING`, `FIXING`, `CONFLICT_RESOLUTION`. Not `PROVISIONING`, the validation states, `CHECKPOINTING`, the merge-lane states or exceptional/terminal states. While the overlay is active only the exceptional states are reachable (it never advances the worker; `ASK` becomes `NEEDS_HUMAN(APPROVAL_ASK)` with the prior state as `resume_state`). | `worker.rs` `is_agent_driven`, `WorkerStatus` |
| DR-D01-6 | Ticket projection when all blockers are `DONE` but integration is not healthy or the ticket is not eligible; and a `REVIEW_STALLED` blocker (the table lists only `FAILED`, `NEEDS_HUMAN`, `CANCELLED`). | Not healthy or not eligible: `PENDING`. A blocker in `REVIEW_STALLED` (a `NEEDS_HUMAN` kind) counts as stuck, so the dependent is `BLOCKED`. A `PAUSED` or `RATE_LIMITED` blocker is not stuck (`PENDING`). | `projection.rs` `project_unstarted` |
| DR-D01-7 | Failure loops inside the worker. Section 3 draws only the forward path and the review/fix loop; section 5 step 7 adds that a failed integration validation returns the worker to `FIXING`. | Added `INTEGRATION_VALIDATION` to `FIXING` (section 5 step 7). `FOCUSED_VALIDATION` has no failure edge (not invented; a failure there is a worker `FAILED` or `NEEDS_HUMAN`). If the Orchestrator needs more retry edges they must be added to the specification. | `worker.rs` `PHASE_EDGES` |
| DR-D01-8 | `STOPPING` to `STOPPING`, and `STOPPING` to `CANCELLED`. | Rejected (not in the table; "any non-terminal to `STOPPING`" read as applying once). Cancel needs `PAUSED`/`NEEDS_HUMAN` first. The `FAILED` reason is recorded outside the machine. | `run.rs` |
| DR-D01-9 | Which resumes are explicit? The DOMAIN_MODEL says "state transitions require explicit causes" and table 1.1 says "Resume or recorded decision". | Callers state a `Cause`. A resume out of `NEEDS_HUMAN` (any kind) needs `Cause::UserDecision`; a resume out of `PAUSED` needs it unless the reason is automatic (`CAPACITY`, `INTERACTIVE_SESSION_UNAVAILABLE`). A system timer therefore cannot silently resume a human-gated state. Spec text should state which pause reasons resume without the user. | `common.rs` `resumes_automatically`, `run.rs`, `worker.rs` |
| DR-D01-10 | Integration health gate and overlay lifetime. | `RunState::transition_with_health` enforces the `RUNNING` to `FINAL_REVIEW` health precondition (the `DONE`-tickets precondition belongs to the Orchestrator); plain `transition` is the structural table. The `WAITING_APPROVAL` overlay ends when the worker leaves its agent-driven state for `PAUSED`, `NEEDS_HUMAN`, `FAILED` or `CANCELLED`; the pending request is owned by the approval broker. The serde shape of the state enums is structural; the persisted/contract wire form is for the ticket that exports it. | `run.rs`, `worker.rs` |
