# D01 Decision Requests

Interpretations D01 had to make where `ORCHESTRATION_ENGINE.md` and `DOMAIN_MODEL.md` are silent or inconsistent. None changes product behavior beyond the conservative reading (reject what is not listed). Each is isolated in one place in `crates/vela-domain/src/state/` so a decision changes one rule. None is blocking.

| ID | Question | What D01 implemented | Where |
|---|---|---|---|
| DR-D01-1 | The diagram in section 1 draws `FINAL_FIXING` to `FINAL_VALIDATION` (`FINAL_REVIEW ⇄ FINAL_FIXING ⇄ FINAL_VALIDATION`) but the normative table 1.1 lists only `FINAL_FIXING` to `FINAL_REVIEW`. | The table wins: `FINAL_FIXING` to `FINAL_VALIDATION` is rejected. Likewise there is no direct `PAUSED`/`NEEDS_HUMAN` entry from `FINAL_*`, `CREATED`, `PREFLIGHT`, `GRAPH_READY`, `AWAITING_START` except via `STOPPING` (Stop All), because the table lists direct entry only from `RUNNING`, `ANALYZING` (`GRAPH_INVALID`) and `STARTING`. | `run.rs` `PHASE_EDGES`, `RunState::table` |
| DR-D01-2 | Which `NEEDS_HUMAN` kinds are valid at run level? Section 3.2 says only `PROVIDER_POLICY_BLOCK` is "valid at worker and run level"; sections 1.1 and 1.2 additionally name `GRAPH_INVALID`, `INTEGRATION_UNKNOWN`, `INTEGRATION_UNHEALTHY` as run-level kinds that are absent from the 3.2 table. | `InterventionKind` has 16 kinds: the 13 of 3.2 plus those 3. A worker accepts exactly the 13; a run accepts all 16 (no further restriction invented). `GRAPH_INVALID` is required for the direct `ANALYZING` to `NEEDS_HUMAN` edge and is rejected as a new gate from every other origin. | `common.rs`, `run.rs` |
| DR-D01-3 | "No transition leaves `PROVIDER_POLICY_BLOCK` automatically; the only exits are resolve to `resume_state` or cancel" versus "any non-terminal to `FAILED`" and "any non-terminal to `STOPPING`". | Both are honored without any automatic exit. From a held block (worker and run) the accepted targets are: `Active(resume_state)` by `Cause::UserDecision` (resolve), `CANCELLED` by `Cause::UserDecision`, `FAILED` (a terminal system outcome that never resumes work), and, at run level, `STOPPING` that keeps the gate. A `STOPPING` that keeps a gate returns only to `NEEDS_HUMAN` with the same kind (or fails), never to `PAUSED` or work. Every other target is rejected with `ProviderPolicyBlockHeld`. | `run.rs`, `worker.rs` |
| DR-D01-4 | The `PAUSED` reason and the `NEEDS_HUMAN` kind per edge, and re-classification of gates. | Kinds are not constrained beyond the explicit rules. `STOP_ALL` is reached only through `STOPPING` (`STOPPING` to `PAUSED` accepts only that reason; `RUNNING` to `PAUSED` rejects it; section 6). Section 3.1 ("any state can transition to ...") is read as: a `PAUSED` worker or run can escalate to `NEEDS_HUMAN`, and a `NEEDS_HUMAN` gate can escalate to `PROVIDER_POLICY_BLOCK` (so a provider block found while paused or gated is recorded, never `RATE_LIMITED`, and is then held). Other gate-to-gate reclassification, and `NEEDS_HUMAN` back to `PAUSED`, are not transitions. A run in `NEEDS_HUMAN` keeps its gate through Stop All: `STOPPING` records the gate and cannot become `PAUSED`. | `run.rs`, `worker.rs` |
| DR-D01-5 | Which worker states are "agent-driven" (so `WAITING_APPROVAL` can overlay them)? | `CONTEXT_LOADING`, `IMPLEMENTING`, `REVIEWING`, `FIXING`, `CONFLICT_RESOLUTION`. Not `PROVISIONING`, the validation states, `CHECKPOINTING`, the merge-lane states or exceptional/terminal states. While the overlay is active only the exceptional states are reachable (it never advances the worker; `ASK` becomes `NEEDS_HUMAN(APPROVAL_ASK)` with the prior state as `resume_state`). The overlay ends when the worker leaves its agent-driven state for `PAUSED`, `NEEDS_HUMAN`, `FAILED` or `CANCELLED`; the pending request itself is owned by the approval broker. | `worker.rs` `is_agent_driven`, `WorkerStatus` |
| DR-D01-6 | Ticket projection when all blockers are `DONE` but integration is not healthy or the ticket is not eligible; a `REVIEW_STALLED` blocker (the table lists only `FAILED`, `NEEDS_HUMAN`, `CANCELLED`); a `BLOCKED` blocker. | Not healthy or not eligible: `PENDING`. A blocker in `REVIEW_STALLED` (a `NEEDS_HUMAN` kind) counts as stuck, so the dependent is `BLOCKED`. A `PAUSED` or `RATE_LIMITED` blocker is not stuck (`PENDING`). `BLOCKED` is not transitive (the table lists only direct `FAILED`/`NEEDS_HUMAN`/`CANCELLED` blockers): a ticket behind a `BLOCKED` ticket is `PENDING`. If the UI should show whole chains below a failed ticket as blocked, the table needs a transitive rule. | `projection.rs` `project_unstarted` |
| DR-D01-7 | Failure loops inside the worker. Section 3 draws only the forward path and the review/fix loop; section 5 step 7 adds that a failed integration validation returns the worker to `FIXING`. | Added `INTEGRATION_VALIDATION` to `FIXING` (section 5 step 7). `FOCUSED_VALIDATION` has no failure edge (not invented; a failure there is a worker `FAILED` or `NEEDS_HUMAN`). If the Orchestrator needs more retry edges they must be added to the specification. | `worker.rs` `PHASE_EDGES` |
| DR-D01-8 | `STOPPING` to `STOPPING`, and `STOPPING` to `CANCELLED`. | Rejected (not in the table; "any non-terminal to `STOPPING`" read as applying once). Cancel needs `PAUSED`/`NEEDS_HUMAN` first. The `FAILED` reason is recorded outside the machine. | `run.rs` |
| DR-D01-9 | Which resumes are explicit? The DOMAIN_MODEL says "state transitions require explicit causes" and table 1.1 says "Resume or recorded decision" / "User cancels the run". | Callers state a `Cause`. A resume out of, or a cancel of, `NEEDS_HUMAN` (any kind) needs `Cause::UserDecision`; the same for `PAUSED` unless the reason is automatic (`CAPACITY`, `INTERACTIVE_SESSION_UNAVAILABLE`). A system timer therefore cannot silently resume or cancel a human-gated state. `FAILED` and cancelling an `Active` worker are system outcomes. The specification should state which pause reasons resume without the user. | `common.rs` `resumes_automatically`, `run.rs`, `worker.rs` |
| DR-D01-10 | Integration health gating and the shape of persisted state. | The public `transition` takes the integration health: `RUNNING` to `FINAL_REVIEW` (section 1.1) and `READY_TO_MERGE` to `MERGING` (section 5 step 2) need `HEALTHY`, and `WorkerStatus::provision` creates a worker only when health permits (section 1.2). The remaining precondition of `FINAL_REVIEW` (every in-scope ticket `DONE`) is not run state and stays with the Orchestrator. The structural table without health is private. The serde shape of the state enums is structural and unvalidated on load (only `WorkerStatus` validates its overlay); the persisted or contract wire form is for the ticket that exports it (no DTO is exported by D01). | `run.rs`, `worker.rs` |
| DR-D01-11 | Scope of `Cause` enforcement. | Enforced only where a human gate is left (resume or cancel of `NEEDS_HUMAN`, resume or cancel of a non-automatic `PAUSED`, `PROVIDER_POLICY_BLOCK` resolve). User-initiated forward edges (graph approval, Build, manual pause) and an automatic-reason pause (`CAPACITY`, `INTERACTIVE_SESSION_UNAVAILABLE`) accept a system cause: the machine records and checks the cause it is given but cannot know who pressed a button, so who may start a build is the Orchestrator's policy. If the specification wants those edges to be user-only, the three edges can be added to the same check. | `run.rs`, `worker.rs` |
| DR-D01-12 | A run that keeps a gate through `STOPPING` and then finds a new need (for example integration health becomes `UNKNOWN` during Stop All reconciliation). | It returns only to `NEEDS_HUMAN` with the same kind, or fails; it cannot record a different kind. The human decision is still required, so no safety property is lost, but the new need is not recorded. Escalation to `PROVIDER_POLICY_BLOCK` is allowed from a plain gate but not from a gated `STOPPING`. A rule for recording additional needs belongs in the specification. | `run.rs` |
| DR-D01-13 | Edges section 3 does not draw: failure of `VALIDATING` after a fix; the conflict-sensitive gate rerun of section 5 step 4 (a re-gate inside the merge lane); resuming into `MERGING` while integration health is not `HEALTHY`. | Not invented. `VALIDATING` has only the forward edge to `CHECKPOINTING` (a failure is a worker `FAILED` or `NEEDS_HUMAN`); `MERGING` has no re-gate state. The health gate is on the entry edge `READY_TO_MERGE` to `MERGING` and on worker provisioning; a worker paused or gated inside the lane resumes "after successful reconciliation" (section 1.1), which re-establishes health first. If the Orchestrator needs these edges, or a health check on resume, they must be added to the specification. | `worker.rs` |
| DR-D01-14 | Pause reasons on a worker and the `ANALYZING` gate asymmetry. | A worker accepts any `PausedReason` directly (the table states reasons per edge only for the run). The `ANALYZING` to `NEEDS_HUMAN` rule (kind `GRAPH_INVALID`) is on the direct edge only: `STOPPING` and `PAUSED` routes with `resume_state` `ANALYZING` accept any kind. Both follow the specification text literally and are listed for the owners to confirm. | `worker.rs`, `run.rs` |

## Follow-ups for specification owners (not code)

- `ORCHESTRATION_ENGINE.md` section 3.2 should list the run-level kinds `GRAPH_INVALID`, `INTEGRATION_UNKNOWN`, `INTEGRATION_UNHEALTHY` named in sections 1.1 and 1.2.
- The section 1 diagram edge `FINAL_FIXING` to `FINAL_VALIDATION` should be reconciled with table 1.1.
- Section 1.1 should say which pause reasons resume automatically (DR-D01-9) and whether a gate may be reclassified (DR-D01-4).
