# F04 Decision Requests (interpretations recorded, none blocking)

Each item is an interpretation of the ticket where the specification is silent or two sentences pull apart. None changes
product behavior; each is cheap to reverse. Reviewers may overrule any of them.

## DR-F04-1: `app.security` is "empty" and also carries the strict CSP

Ticket section 5 asks for a strict CSP in `tauri.conf.json` and, separately, for an "empty `app.security`" section so
Z01, Z02 and the lifecycle tickets edit disjoint keys. Taken literally these conflict. Resolution: `app.security` holds
only the keys F04 owns (`csp`, `freezePrototype`); `bundle` and `plugins` are `{}`. Later tickets add their own keys
(`assetProtocol`, `pubkey`, and so on) beside them and never edit `csp`. `devCsp` is deliberately absent: with a dev
server the page is not served by the Tauri protocol, so the CSP applies to the production bundle only.

## DR-F04-2: the command is `diagnostics.ping`, wire name `diagnostics_ping`

The ticket says "one example command (ping)". The registry (`command_registry.rs`) requires dotted names of at least two
segments, and a Tauri command is addressed by a Rust function name. So the registry name is `diagnostics.ping` (group
`diagnostics`, the group that later owns `diagnostics.export`), and the wire name is the dotted name with `.` replaced by
`_`. The mapping is one rule in `commands::wire_name` (Rust) and `wireName` (TypeScript) and the group is the first
segment.

## DR-F04-3: the example event is not an `EventEnvelope`

The event vocabulary is closed (`SYSTEM_ARCHITECTURE.md` section 4), so F04 cannot add a kind for the example. The
example event `vela:ping` therefore carries its own small payload (`PingEvent`) on a separate event name. The real
journal feed (`EventEnvelope`) keeps its single channel and is wired by F08.

## DR-F04-4: example DTOs are hand-written in TypeScript, pinned by a Rust test

`packages/contracts/src/generated` is owned by `vela-domain` and a `cargo test` there fails on any file it does not
generate, so F04 cannot put `ts-rs` output of a `vela-desktop` type there. The three example types
(`PingRequest`, `PingResult`, `PingEvent`) are hand-written in `packages/contracts/src/commands/diagnostics.ts`; a Rust
test pins their JSON shape and the contract test pins the command names. A later ticket that wants generated command
DTOs needs a second generated directory (a specification change).

## DR-F04-5: the contracts package gains a second wildcard export

Callers need to import `commands/diagnostics`. `packages/contracts/package.json` `exports` gains `./commands/*` next to
`./generated/*`, and `skeleton.test.ts` is extended (not relaxed) to assert both. There is still no barrel.

## DR-F04-6: the permission manifest is hand-written, one file per group

`SHARED_SURFACE_PROTOCOL.md` section 4 wants one committed permission file per group. Tauri's
`AppManifest::commands` generates one file per command into `permissions/autogenerated`, which does not match, so the
manifest is `permissions/diagnostics.toml` with the identifier `allow-diagnostics-ping` (same shape Tauri generates).
`tauri-build` validates every identifier in `capabilities/*.json` against it, so a misspelled grant fails the build.

## DR-F04-7: pre-declared sorted registries instead of a growing list

"Adding a command group or a plugin requires adding only that group's or plugin's own file" cannot hold for a list
that must be edited to add an entry. Both registries are therefore pre-declared for every group and plugin that
`SHARED_SURFACE_PROTOCOL.md` names (15 groups, 7 plugins), each backed by a stub file the owning ticket fills in:
`commands/mod.rs` routes by the first segment of the wire name, `plugins/mod.rs` has one sorted array.
