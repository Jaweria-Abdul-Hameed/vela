# D05 Decision Requests (non-blocking)

Ticket: `docs/issues/graph/tickets/D05.md` (policy engine core). Each entry is an interpretation made where the specifications
are silent or in tension. None changes product behavior beyond what the ticket and ADRs state; each can be overruled by the
owner with a small follow-up. Nothing here reopens an accepted ADR.

| ID | Question | Chosen | Alternative and consequence |
|---|---|---|---|
| DR-D05-1 | Acceptance says "no input yields ALLOW outside the confirmed profile", while `SECURITY_AND_PERMISSIONS.md` also lists file edits in the worktree and non-destructive Git inspection as auto-allow examples. | `ALLOW` exists for exactly two bases, both in a `TRUSTED` repository: a command equal to a confirmed-profile entry (exact normalized executable, arguments and directory), and a **structured** read or write inside the worktree (the path-scoped write rule of ADR-018). A command never allows on the second basis. Git inspection is **not** auto-allowed by the core; `git status` and similar are `ASK` unless the user confirms them into the profile. | Seeding a read-only Git set into the profile (for the user to confirm) is a settings-ticket decision. Making inspection a built-in `ALLOW` would break the literal property. |
| DR-D05-2 | `COMPONENT_SPECIFICATIONS.md` C03 says "destructive classes are DENY"; `SECURITY_AND_PERMISSIONS.md` lists "destructive database/infrastructure operations" and "operations outside workspace" under **Ask**, and "deleting unrelated user data", "force-pushing", credential extraction and "disabling security controls" under **Deny**. | `DENY`: credential access, security-control changes, force and remote-deleting pushes, history- or work-discarding Git, deletes outside the worktree or of the worktree itself or an unplaceable absolute location, disk-destroying tools, writes to protected locations. `ASK`: database, cloud and cluster destruction, outside-root writes and reads, in-worktree deletes, system configuration, network access, nested shells, installs, unknown executables, anything unparseable. | Moving a class between tiers is a one-line change to `defaults.rs`. |
| DR-D05-3 | The engine is pure and cannot resolve symbolic links, junctions or 8.3 names. | Resolution is lexical (ASCII case-folded, `.`/`..` collapsed; a non-ASCII case difference is a different path to the engine, which errs toward "not inside"). Anything it cannot establish (device namespaces, alternate streams, short names, `~`, rooted-on-current-drive, drive-relative) is `Unresolvable`, which is never inside. **Precondition on callers:** paths and the worktree root arrive with links already resolved by the process and Git adapters. | A link inside the worktree that points outside is invisible here; the adapter's resolution (S and A tickets) must close that. |
| DR-D05-4 | Context inputs list "branch/remote"; the default examples include ordinary commits and normal pushes to permitted branches. | Agent-issued `git commit`/`git push` are `GitMutate`/`GitPush` = `ASK` unless in the confirmed profile; the core takes no branch or remote input. Vela performs checkpoint commits and pushes itself (ADR-015), under its own gates. | A permitted-branch rule would be an additional `ALLOW` basis and must be added to the property, not smuggled in. |
| DR-D05-5 | `run mode` is a context input. | Carried in the context and in the hook table so the broker and journal can record it; no rule varies by mode in D05 (the specifications do not define a mode-specific allow set). | A wider Autonomous allow policy needs its own specified basis. |
| DR-D05-6 | ADR-009 NPP-2 requires the native envelope to contain no class that policy classifies `ASK`/`DENY`, while ADR-018 generates a path-scoped write allow for the whole worktree (which contains `.git`, `.agents`). | `NativeAllowRule::WriteWithin` carries `WriteExclusions` (protected directories, credential directories, file names, prefixes and extensions, from the classifier's own tables) so the adapter can add path-scoped deny rules; the hook denies them regardless (a hook `deny` is a hard block, ADR-018 section 3). Native allow commands are emitted only for profile entries the engine itself allows. | Whether native deny-over-allow holds in practice is the `[U]` spike S-NATIVE-POSTURE; not claimed here. |
| DR-D05-7 | The ticket lists "rule schema persisted by the settings store" and "rule-table format shared with vela-hook" but its write surface is `policy/**` only. | Rules, profile entries and the hook table derive `serde` (serde-only so the `hook-table` configuration builds); no `ts-rs` DTO is exported and `packages/contracts` is untouched. | If the settings UI needs rule types in TypeScript, the contracts regeneration belongs to the ticket that owns that surface. |
| DR-D05-8 | In `cmd`, a bare executable name resolves in the working directory first. | Profile matching is on the normalized name and directory only. Agent commands run in PowerShell (CURRENT_STATE constraint 5), where the working directory is not searched; the profile is confirmed by the user for a `TRUSTED` repository (ADR-013). | A planted `npm.cmd` in a trusted worktree is a trust-model matter, not a policy-engine one. |
| DR-D05-9 | The credential, protected-location and tool tables cannot be exhaustive. | They are conservative and explicit; everything not listed is `ASK` (unknown executable or outside-root path). Notably `.env`, `.npmrc` and key-file extensions are `DENY` to read even inside the worktree. | Over-denial of a legitimate `.npmrc` read is possible and safe; the user-visible remedy is to do it themselves. |
| DR-D05-10 | "Rule conflicts are reported at creation time" does not say what happens next. | Order resolves overlaps (first match). A rule wholly covered by an earlier rule with a **different** outcome is refused (`Shadowed`: it could never apply); same-outcome coverage (`Redundant`) and partial overlaps with different outcomes (`Overlap`) are reported and accepted. User rules may only `ASK`/`DENY` and sit after the built-in `DENY` tier and before everything that can allow. | Refusing overlaps too would reject the built-in set (specific `ASK` rules sit under profile `ALLOW`). |
| DR-D05-11 | `git checkout <path>` overwrites local edits with no flag, and a path cannot be told from a branch name lexically. | `git checkout` is `DENY` (history- or work-discarding) unless it creates a branch (`-b`, `-B`, `--orphan`), has no operands, or has one plain branch-like operand (no `/`, `\`, `.`). `git switch` is the branch-only form and stays `ASK`. `git rm -f` and `git branch -D`/`-df` are `DENY`. | Branch names containing `/` or `.` need `git switch`; relaxing this needs a path-aware adapter. |
| DR-D05-12 | `/word` is a switch in `cmd` and a rooted path in PowerShell. | Dialect-aware: `cmd` reads it as a switch; PowerShell reads it as a rooted path except for a short list of native tools (`robocopy`, `xcopy`, `attrib`, `icacls`, `takeown`, `tar`, `7z`); an unspecified dialect reads only `/s`-sized words as switches. So `rd /s /q build` is `DENY` when issued in PowerShell (where it would delete rooted paths) and `ASK` in `cmd`. In `cmd`, a first word is split at a slash (`rd/s/q`). | Agents run in PowerShell, so cmd-style deletes fail closed and the agent adapts. |
| DR-D05-13 | Name tables (`format`, `cmdkey`, ...) versus repository scripts that share the name. | Tables apply to bare names and absolute paths outside the worktree; a path-qualified executable inside the worktree is an unknown executable (`ASK`), and can be confirmed into the profile. | A planted program can still pose as a system tool; it is asked, not denied. |
| DR-D05-14 | A command whose working directory cannot be resolved has no base for relative targets. | Relative delete targets are `DENY` (cannot be placed), other relative targets are unplaced (`ASK`); absolute targets still resolve. | |
